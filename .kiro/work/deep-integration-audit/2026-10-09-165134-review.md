The branch lands F-1, F-2, F-4, F-5, F-6, F-9 and F-10 from the settled design as seven production commits plus one test-fixture-realism commit, across nine production files and eleven test files. ### The pre-existing failure, and why it is not this branch's

"One test fails" is indistinguishable from a regression until its provenance is established:

```
merge-base(origin/stack, HEAD) = 1102da71   # workflow file PRESENT
HEAD                           = f958c657   # workflow file PRESENT (inherited)
origin/stack                   = 0a59ecf8   # workflow file ABSENT (b350ceb7 removed it)
```

`git diff origin/stack...HEAD --name-only` contains no path under `.github/` and no path under `scripts/`, so neither half of the assertion — the declared roles nor `fix_github_oidc_trust.ROLES` — was touched by this work. FEAT-001's `findings` recorded this failure at the post-merge baseline and set every later FEAT's gate as "`passed >= N` with that one failure and no other"; FEAT-002 through FEAT-004 each honoured it with a strictly rising count (10469 → 10502 → 10509). Upstream has since deleted the workflow, so the next integration of `origin/stack` clears it with no action here.

### The arm F-1 correctly left alone

The `batchHandle` arm at `:657` has no `applied: 0` — it carries `outcome["applied"]` — and was not given a `reason`, matching the plan's instruction to leave it untouched. The `validationErrors` field returned from `_batch_requests` is a return value, not a log line, and is unchanged from the base branch, so the "no Graph body logged" property is not quietly undermined by a return path.

### F-2's fail-open default is the load-bearing choice

Step 5 is fail-open by contract because a raise reaches the handler's top-level `except`, returns 500, and lets the idempotency lease lapse so Razorpay replays a captured payment. `native = False` is set before the `try`, so the only path to suppressing a review is a successful read that says `nativeCatalogService`; a transient throttle sends the review. The inverse default — skip on error — would have silently suppressed legitimate website review requests under storage pressure.

`test_the_guard_catches_the_storage_type_and_not_everything` asserts at source level that the block between `native = False` and the `post_payment_complete` log contains `except order_keys.OrderIdentityUnavailable:` and does not contain `except Exception`. A later tidy-up to a bare catch fails the suite rather than passing by behaving identically today.

### F-6's eligibility scan walks every page when the answer is no

`has_prior_order` pages until it finds one qualifying order or exhausts the index, with a `ConsistentRead` `get_item` per projected row to re-verify ownership. It returns on the first match, so the only full walk happens for a customer who has no prior order, bounded by that customer's own order count. This is the designed trade: keeping both questions in one function is what made the naive version of the fix purchase-blocking for legacy-only customers.

### F-10 when the review send itself fails

The deferred check is `if accepted and not link_sent and not delivered`. When the review send is not accepted the function returns `VAULT_REVIEW_PENDING`, so the deferred reason is not logged in that case. The defect F-10 exists to close — a purchase that delivered nothing reported as `VAULT_READY` — is still closed, because `VAULT_REVIEW_PENDING` is not a success outcome either. The design specified the review send must still happen and that the outcome is what changes; both hold.
