# Every WhatsApp menu deleted, with a plain-text stand-in in its place

Four commits (`c3a6b165`, `365bbd18`, `ef79ec16`, `5572b213`) remove every WhatsApp menu definition and the whole menu routing surface from the two messaging Lambdas, and replace each former menu send with one plain-text line. The inbound handler loses the one-menu config, the retired main menu, the customer-service and Bharat Stack submenus, the language/region picker, every menu getter, the ~60-id `MENU_TO_KEYWORD` dispatch table and `_send_interactive_list` itself; `whatsapp-calling` loses all three `wd_menu` template sends and the dead `_send_ivr_menu`. The trigger keyword sets stay and only their bodies change, which is what keeps `menu` / `hi` / `get started` answering instead of erroring. This pass reviews the second iteration: `5572b213` closes the two test-coverage gaps raised previously.

Watch for: nothing blocking. Both prior findings are resolved and verified (confirmed). The post-call WhatsApp follow-up is now a text send, so it needs an open 24-hour window and a caller who has never messaged the business will not receive it (confirmed, deliberate, documented, and SMS/RCS still reach them). An unknown `button_reply` id still gets no reply, but that is pre-existing and byte-identical on both sides of the diff (confirmed).

**Verdict**: APPROVED

### The three trigger sets stayed, and that was the right call

The deletion list asked for `BUTTON_MENU_TRIGGERS` to go while the replacement list required typing `menu` / `hi` / `get started` to reach the catch-all. Those cannot both hold — you cannot route a trigger word without a trigger-word set. The resolution keeps `HI_KEYWORDS` (1920), `BUTTON_MENU_TRIGGERS` (1664) and `CUSTOMERSERVICE_KEYWORDS` (1969) with their guard expressions byte-identical, and swaps only the body. The evidence that no guard string moved is that `tests/test_own_prefill_triggers_menu.py::test_menu_sets_use_the_fallback` passed *without* being edited; only its docstring and one class name changed afterwards.

This matters beyond tidiness: `customerservice` is a live ice breaker and slash command on both numbers, read off Meta's `conversational_automation`. Dropping the trigger would have stopped answering something customers are actively invited to tap.

### `_handle_list_reply` is now strictly better than before

```
tap any row id  →  list_reply_received log (listId in full)  →  _send_menu_placeholder
```

The function keeps its name and all five parameters because callers pass by keyword at 1455-1461; `sender_phone` is deliberately unused. `listId` stays unmasked, correctly — a row id is not a secret and is the only correlation handle on a tap from chat history.

The accepted consequence is real and worth restating: a tap on a row still sitting in a customer's history no longer reaches a flow or a payment. `menu_pay` no longer invokes `wecare-invoice-engine`. Every typed-keyword equivalent is untouched (`pay`, `store`, `gift card`, `faq`, `about`, `help & about`, `BHARAT_KEYWORDS`, all of `DEFAULT_FLOW_TRIGGERS`), which is exactly what `TestNothingBecameUnreachable` now pins rather than leaving to prose.

### The two placeholder constants are a genuine drift hazard, and it is pinned

The handlers share no module, so each carries its own module-level copy of the string. A divergence would make one WABA answer differently from the other with nothing at runtime noticing. `test_both_lambdas_hold_the_same_string` loads both modules and compares; verified independently here as `True` for `"We're refreshing our menu - please type *menu* and we'll help you."`.
