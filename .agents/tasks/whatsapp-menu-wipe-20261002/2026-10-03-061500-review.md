# Delete every WhatsApp menu and answer with text instead of silence

Three commits (`c3a6b165`, `365bbd18`, `ef79ec16`) remove every WhatsApp menu definition and every menu routing path from the two messaging Lambdas, replacing each former menu send with one plain-text catch-all. The inbound handler loses 1087 lines: the one menu, the retired main menu, the customer-service and Bharat Stack submenus, the language/region picker, all five getters, the ~60-entry `MENU_TO_KEYWORD` dispatch table, `_send_interactive_list` itself, and the unreachable tail of `_process_ai_automation`. The calling handler loses all three `wd_menu` template sends. A third commit corrects comments in `ai-generate-response` and `outbound-whatsapp` that had become false. Both Lambdas survive and import; the IVR button menu is untouched; nothing was deployed.

Watch for: three tests in `tests/test_one_menu.py::TestNothingWasTakenAway` were deleted even though they assert no deleted menu and still pass against the post-wipe tree (**confirmed** — reconstructed and run). They were the only coverage of the wipe's central safety claim, that every former menu row remains reachable by typed keyword. The calling-handler half of the change has zero test coverage (**confirmed**) — `test_calling.py` patches the caller out, so the new `_send_menu_placeholder_text` and the `wd_menu` removal are asserted nowhere. Separately, the dashboard still presents editable "Main Menu" and "Selfservice menu" forms writing to SystemConfig rows that no backend code reads any more (**confirmed**), and the Scripts page still tells the owner that typing `hi` sends an Interactive List.

**Verdict**: NEEDS_CHANGES

## High-level view

The deletion itself is complete and correct. Every symbol named in `plan.md` is gone, verified by grep, by module attribute check on the imported handler, and by AST walk for `MENU_TO_KEYWORD` assignments and `_send_interactive_list` calls at any nesting depth. `_process_ai_automation` is now a two-statement stub (docstring, `return None`), which is what let the language picker go without leaving dangling references.

The silence problem that motivated the task is fixed rather than moved. The prior concurrent commit `ed1f3911` had emptied `DEFAULT_ONE_MENU['sections']` while leaving the machinery, and `_send_interactive_list` short-circuited on an empty sections list, so a greeting sent nothing. All seven former send sites now call `_send_menu_placeholder`, and `_handle_list_reply` — which previously ended in a `list_reply_unhandled` log and no reply — answers too. That is a net improvement over the pre-wipe state, not just a restoration.

Keeping the trigger sets while changing only their bodies is the right resolution of the task's internally contradictory deletion list. `HI_KEYWORDS`, `BUTTON_MENU_TRIGGERS` and `CUSTOMERSERVICE_KEYWORDS` are live on Meta as QR prefills, ice breakers and slash commands; removing them would stop answering something customers are actively invited to tap. The guard expressions are byte-identical, evidenced by `test_own_prefill_triggers_menu.py` passing unedited.

The calling handler's replacement is a text send where a template used to be, and the consequence is stated honestly in both the code and the task record: a post-call follow-up now needs an open 24-hour window, so a caller who never messaged the business is no longer reached on WhatsApp. Since `wd_menu` was deleted at Meta, the previous send failed 100% of the time, so this is strictly better. SMS and RCS still run.

The keep list is intact. `_SHARED_IVR_MENU`, `IVR_MENUS`, `IVR_DEFAULT_MENU`, `IVR_RESPONSES` (still holding `ivr_callback`, `ivr_support`, `ivr_ai`, plus `ivr_sales`) and `_get_ivr_menu` all survive, with `_get_ivr_menu` still called from `_auto_pickup_and_play`. So do `_react_thumbs_up`, `_is_auto_thumb_reaction_enabled` and `_is_postcall_wa_enabled`.

Nothing reached production. All four touched functions report identical `CodeSha256` on `$LATEST` and on the version their `live` alias points at, last modified 2026-10-02T02:27–02:29 UTC — before these commits. The three commits are also unpushed, so the menus remain live on both WABAs.

The gap is in what pins the change. The inbound half got a purpose-built invariant test; the calling half got nothing, and a scope-guard class that was not about menus at all was deleted along with the menu tests.

### Every answer path reaches the catch-all

```
text "hi" / "menu" / "/menu" / QR prefill   -> HI_KEYWORDS            -> placeholder
button "Get Started" / "Selfservice"        -> BUTTON_MENU_TRIGGERS   -> placeholder
text "customerservice" / "/service"             -> CUSTOMERSERVICE_KEYWORDS   -> placeholder
request_welcome (tapped Start)              ->                           placeholder
brand-new contact, any message type         ->                           placeholder + welcomeSent
button_reply "followup_explore"             ->                           placeholder
list_reply, ANY row id                      -> _handle_list_reply     -> placeholder
post-call SIP / call connect                -> _send_menu_placeholder_text (text via Meta)
```

The `welcomeSent` write on the brand-new-contact path is kept, so the placeholder does not re-send on every message from a new contact.

One asymmetry, **pre-existing and unchanged by this diff**: a `button_reply` whose id is neither `ivr_*`, `followup_explore` nor `followup_done` falls out of the interactive block, and because `msg_type` is `interactive` rather than `text` the keyword branch is skipped, so it gets no reply. `modules/content.py` forwards ids prefixed `opt_`, `rate_`, `menu_`, `lang_`, `store_` as text, which implies such ids existed historically. The pre-wipe code behaved identically — the `button_reply` branch never consulted `MENU_TO_KEYWORD`, which only ever handled `list_reply` — so this is out of scope here, but it is the one tap that still produces silence.

Also pre-existing: `_load_fallback_message` has no caller in either the current tree or at `2c6cfea3`, so `DEFAULT_FALLBACK_MESSAGE` is never sent and an unmatched text message gets nothing. `test_own_prefill_triggers_menu.py` documents that as deliberate.

### The deleted tests that were not menu tests

`tests/test_one_menu.py` held six classes. Five asserted deleted menus and go with them correctly. `TestTheRivalMenuIsGone::test_ai_handler_defines_no_menu` was carried into the new file; its companion `test_ai_handler_returns_to_the_one_menu` was correctly dropped, because it asserted that `menuResponses` point at `show_main_menu` "which the inbound handler resolves to the one menu" and that subject no longer exists.

`TestNothingWasTakenAway` is the exception. Its three tests assert:

- `DEFAULT_FLOW_TRIGGERS['schedule_appointment']` still carries `appointment`, `schedule appointment`, `book appointment`, `book a visit`, `visit`
- `leave review`, `order notes` are in the flow keywords, and `my id`, `store`, `gift card`, `bharat stack`, `about` are in their respective keyword sets
- `_send_help_about`'s body still names `*my id*`, `*store*`, `*gift card*`, `*order notes*`, `*review*`, `*bharat stack*` — the only place a customer is told these exist

Every subject survives the wipe. Reconstructed from `2c6cfea3` and run against the current tree: **4 passed** (the three plus the carried-over AI check). This is exactly the "nothing becomes unreachable by every route" claim that `plan.md`, the commit message and the FEAT findings all rest on, and it is now asserted only in prose. `test_menus_are_deleted.py::test_typed_keyword_flows_survive` is a much weaker stand-in — it checks only that `DEFAULT_FLOW_TRIGGERS` is non-empty and the getter is callable.

The brief's criterion is that tests be deleted "only where they exclusively asserted a deleted menu". This class did not.

### The calling handler changed two live paths with nothing pinning them

`test_calling.py` patches `_send_call_whatsapp_notification` at four sites and never inspects its arguments, which is why the pass count was identical before and after (229). The practical effect is that FEAT-002's whole change is unverified by the suite: no test asserts `wd_menu` is gone, that `_send_menu_placeholder_text` uses `_meta_api_call` rather than `_send_via_aws` (the precondition that keeps the auto-👍 working, since a reaction's `message_id` must belong to the same `meta_id`), that both `_handle_post_call_sip` and `_send_call_whatsapp_notification` call it, or that the IVR symbols survive. The inbound half got precisely this treatment in `test_menus_are_deleted.py`; the calling half got only a reworded docstring.

### Structured error detail narrowed on the failure path

`_send_menu_placeholder_text` returns `''` on failure and swallows the Meta response, so `call_wa_template_FAILED` no longer carries `errorCode`, `errorMessage`, `httpStatus` or `fullError`, and `_handle_post_call_sip`'s warning no longer includes the result. The cause is not lost — `_meta_api_call` logs `Meta API error {status}: {body}` itself, and maps known codes through `META_CALLING_ERRORS` — but it is no longer correlated into the structured event that carries `requestId`. This matters more than it did, because the expected failure mode just changed from "template rejected" to "closed 24-hour window", and 131047 is precisely the code that distinguishes that from a token or permission failure. Reported, not required.

The retry condition also broadened from `if not msg_id and api_result.get('error')` to `if not msg_id`, so a response with no message id but no error now retries once. Harmless and arguably more correct.

### Stale admin surfaces the wipe left behind

The deleted getters read four SystemConfig rows: `welcome_message_config`, `customerservice_menu_config`, `bharat_stack_menu_config`, `bot_language_picker_config`. No backend code reads them any more, so no row can resurrect a menu — but the dashboard still writes them:

- `src/pages/workspace/engage/whatsapp/auto-response.tsx` renders editable Main Menu and Selfservice menu forms with `saveMainMenu` / `saveSsMenu` handlers that toast "Main menu saved"
- `src/pages/workspace/engage/whatsapp/scripts.tsx:62,71` lists both under category `Menu` with `messageType: 'Interactive List'` and trigger `hi / menu / start / Explore More button`, marked `editable: true`
- `src/pages/workspace/dashboard/index.tsx:1894,1897` offers `welcome_message_config` ("Header, body, footer, button text, sections & rows for the main menu") and `bot_language_picker_config` as editable config

The owner's next step is to design a replacement menu, and the Scripts page currently misreports what a greeting does. TypeScript was outside this task's declared scope, so this is reported rather than required, but it should be the first thing the fresh-menu work reconciles.
