# Customer-experience upgrade: Request/Zip nav, Perks page, blog contributions, and gated coupon/gift-card redemption (v1)

The branch delivers the in-scope slice of the WECARE.DIGITAL customer-experience brief: the customer nav group is relabelled to the singular "Request" and gains a Zip entry; a public `/zip` request/delivery/pickup hub and a public `/perks` gift-cards/rewards/offers page are added (the latter repairing the dead `/gift-card` CTAs); every blog post gets a "Support this work" voluntary-contribution block backed by a full `BLOG_CONTRIBUTION` payment server; and the Section 2 coupon + gift-card redemption authority is built as a server-authoritative, integer-paise library with reservation/rollback/commit/refund/reconciliation. All payable work is kept behind the existing disabled checkout gate and delivered as source + runbooks because the sandbox has no AWS/Wix credentials. The money-safety core is implemented with real intent: the browser never controls a trusted amount, verification requires an authoritative capture readback, and the webhook re-derives amounts from stored records.

Watch for: (**confirmed**) the Section 2 `redemption.py` authority and the `prepare_contribution`/`verify_contribution_callback` entry points are **not wired into any live HTTP handler** — `website_checkout.py` and `checkout/handler.py` are byte-unchanged, so only the contribution *webhook settlement* path is reachable from a real Lambda; the rest is tested library code awaiting the AWS/Wix wiring the runbooks describe. (**confirmed**) the contribution `verify_contribution_callback` and `commit_redemption`/`refund_redemption` have no caller yet, so the gift-card commit-on-capture leg has no live webhook branch (unlike the contribution settle leg, which does). Both are consistent with the "built-but-gated, blocked-on-environment" scope, not defects — but they are the seams a reviewer must confirm are intentional before this is called complete.

**Verdict**: APPROVED

## High-level view

The nav change is a label-and-grouping edit only: `heading` goes from `Requests` to `Request`, a `Zip` row is added after Orders, and a new `Perks` group sits immediately above `Legal Stuff`. No internal `customerservice` identifier, config group id, or workspace route is touched, honoring the migration-safety carve-out. Both new public pages are registered across all three required lists (`PUBLIC_PAGE_META`, `PUBLIC_EXACT`, `public-pages.json` + a `perks` group), so neither serves the staff shell at HTTP 200.

The `/gift-card` audit is handled correctly: the three active backend CTAs (WhatsApp handler, AI response handler, SEO site map) are repointed to `/perks/`, and `/perks` becomes the real destination with Gift Cards reachable at `#gift-cards`. No third-party provider name appears in any customer-facing surface or page source.

The blog contribution backend is a faithful sibling of `website_checkout`: the same gate contract, HMAC over the server-stored order id, a mandatory authoritative capture readback, and a webhook that re-derives the amount from the stored `BLOGCONTRIB#` record rather than from `payment.notes`, settles exactly once, quarantines unresolvable captures, and creates no Wix order. The server owns the amount via a preset-set-plus-bounds validator that rejects floats, bools, strings, and out-of-range values; the frontend config mirrors it exactly.

The coupon/gift-card redemption authority models a coupon as a price change that feeds the fee/GST calculator and a gift card as tender subtracted from the final payable, both server-authoritative in integer paise. `cart_v2`'s blanket gift-card rejection is retained unchanged — the split is real: the standalone cart contract still rejects unverified gift cards, and the verified redemption is applied only server-side. Reservation is atomic and double-spend-safe via a card-level lock keyed by a non-reversible fingerprint, with rollback, exactly-once commit (including a zero-remaining attempt-keyed path), refund, and reconciliation. A fully gift-card-covered order yields `requires_gateway=False` yet is never treated as a captured payment.

The frontend surfaces (contribution block, cart redemption panel) send only a code/amount *request*, render only server-decided amounts, never fetch at prerender time, and degrade to an honest "not available" state for the gate-off/absent-endpoint/network-failure cases — never fabricating a paid or thank-you state. The `/zip` coming-soon affordances are inert `<span aria-disabled>` elements with no href. Out-of-scope `terms.ts` and `privacy.ts` are byte-unchanged.

### Blog contribution: server owns the amount, verification needs a capture readback

`validate_contribution_amount` is the trusted gate: INR only, `positive_paise` rejects bools/floats/strings/non-integers, presets are exact-match accepted, and any other value must fall in `[1000, 10_000_000]`. The browser value is only a request; the frontend `contribution.ts` holds the same presets and bounds, and `test_server_presets_mirror_the_frontend_contract` pins them equal so a client-side widening cannot drift from the server.

`verify_contribution_callback` resolves the binding by the *stored* order id (an unknown presented id is a mismatch), re-checks the stored account/mode so a test-mode binding cannot settle live, HMACs over the stored order id, and treats a valid signature only as a trigger — a capture readback whose amount/currency must equal the stored binding is still required before `VERIFIED_PAID`. The tests drive each branch: signature-valid-but-not-captured, bad signature (capture must not even be checked), amount mismatch, currency mismatch, and the test-mode-cannot-settle-live case.

The webhook settlement mirrors the `partner_billing.topup` pattern: a stored `BLOGCONTRIB#` record must exist (notes are a routing hint only), the amount is re-derived from that record and verified against the provider, the payment-id-keyed claim is made before the settle write so a replay settles exactly once, and an unresolvable capture (no record / amount mismatch / not captured / wrong currency) is quarantined. `test_webhook_notes_amount_is_not_authority` sends a forged `notes.amount` of 990000 against a stored 4900 and asserts it settles at 4900 — this fails if someone reverts to trusting the notes amount. `test_real_webhook_handler_routes_blog_contribution_and_settles` drives the actual `_handle_payment_captured` with the fake table and a stubbed `payment_is_captured`, confirming the routing branch and the no-order-side-effect guarantee end-to-end.

```
browser POST {purpose,postId,slug,amountPaise,currency}
        │  (amountPaise is only a REQUEST)
        ▼
prepare_contribution ── gate OFF ──► PAYMENT_INITIATION_DISABLED (no gateway order)
        │  gate ON
        ▼
create_order ─► bind (server amount) ─► browser-safe options {keyId,orderId,amountPaise,...}
                                              │
Razorpay capture ─► webhook payment.captured (notes.purpose==BLOG_CONTRIBUTION)
        │
        ▼
settle_contribution_capture
   1 stored record exists?         no ─► quarantine
   2 amount re-derived from record, verified vs provider; mismatch ─► quarantine
   3 payment-id claim before settle ─► SETTLED once / DUPLICATE on replay
   (no Wix order, no public order number)
```

### Coupon vs gift card: the right side of the fee calculator, retained cart rejection

`apply_coupon` returns the provider's authoritative discount (never a browser figure — the revert-check asserts the function signature has no client-discount parameter and that the provider's small discount wins), clamps a discount larger than the collection to zero-floor, and returns the discounted collection that *feeds* `checkout_pricing`. `verify_gift_card` subtracts a verified `min(balance, total)` from the already-computed total as tender, with the identity `redemption + payable == total` re-checked in `__post_init__`. The 121481-paise fixture is preserved and the tests exercise exact integer-paise subtractions against it (21481 → 100000 remaining; full-cover → 0 remaining).

`cart_v2.py` is byte-unchanged, so the standalone cart contract still raises `CartContractError` on any `paymentSummary.giftCards`/split/deferred payment — the blanket rejection the brief says must not be deleted. The split is genuine: the cart rejects a gift card it tried to self-apply; `redemption.py` applies one the server verified, after an authoritative balance readback.

### Reservation, concurrency, and the zero-remaining path

The reservation is keyed by a SHA-256 fingerprint of the card code (the raw bearer code is never a storage key) plus the attempt id. A card-level `GIFTCARDLOCK#` row is claimed atomically before the per-attempt reservation, so the same card cannot fund two live attempts — the second gets `LOCKED_ELSEWHERE`/`CONCURRENT`. `test_revert_check_concurrent_card_cannot_double_spend` applies one card to two attempts and asserts the second is refused; removing the cross-attempt guard makes it pass through and the test fails. Release is conditional on `RESERVED` (double release is a harmless no-op and never undoes a commit), commit is exactly-once per payment id, and the zero-remaining case keys the commit on `attempt:<id>` because there is no payment id. `test_revert_check_gift_card_zero_remaining_still_gated` asserts a fully-covered order has `requires_gateway=False` yet is not a captured payment and reconciles exactly — the invariant that a zero-remaining order still settles through the authoritative path rather than auto-completing from browser state.

### Frontend surfaces degrade honestly and never fabricate payment

`BlogContribution` fetches only on a user click (not at prerender, which would break the static export), posts the requested amount as a *request*, and resolves `PAYMENT_INITIATION_DISABLED` / rejected / ambiguous / unknown / 404 / network-failure all to the same honest "Contributions are not available right now." `CHECKOUT_OPTIONS_READY` sets a "ready" phase but explicitly does not render a receipt/thank-you — `test ... does not render a receipt even when the backend reports it is ready` asserts "ready" never reads as paid. The cart `RedemptionPanel` sends only `{kind,action,code}` — no amount, discount, or price leaves the browser — and renders only server-returned paise, with an honest unavailable state and no provider name. `CartRedemption.test.tsx` asserts the body carries no amount and that no `giftup` string appears.

### Tests are meaningful, with one naming defect

The backend suites drive the real functions and the real webhook handler against the in-memory `FakeDynamo` with a stubbed provider readback, cover the full edge-case matrix (partial/full/zero-remaining/invalid/expired/insufficient/duplicate/concurrent/rollback/refund/reconciliation for gift cards; the gate, callback, and webhook branches for contributions), and the three named revert-checks each fail if their guard is reverted. 105 backend tests pass (including the 121481 fixture); 49 of the new frontend tests pass. The one weak spot: `test_refund_releases_a_committed_redemption_back_to_the_card` refunds a *reserved* row, not a committed one — its own inline comment concedes this — so it does not actually prove a committed redemption is released on refund; the real refund-of-committed path is a conditional no-op that goes unasserted.

### Unrelated changes bundled in

`StructuredDataService.test.ts` gains 4 lines for the two new pages' schema, and `test_checkout_package_completeness.py` adjusts by 6 lines — both are consequences of the new modules/pages rather than independent changes. No unrelated refactors are bundled.
