# Geocoding library import + left-card place metadata and PM2.5 status label on VayuLok (v2)

Two follow-up commits land on top of the already-APPROVED two-column restructure. `39b82f16` fixes a real geocoding initialization defect: the map init effect imported `maps`/`marker`/`places` but took `Geocoder` from the raw namespace and never imported the `geocoding` library, so under the modern `loading=async` loader `geocoder.current` could be null in a live browser — breaking reverse-geocode-on-map-click and the autocomplete→geocoding search fallback while CI stayed green because the test seeded `google.maps.Geocoder`. The fix imports `geocoding` in init, adds an `ensureGeocoder()` helper the search fallback uses, and surfaces non-`ZERO_RESULTS` geocode statuses as the existing amber `unavailable` status. `a7c39664` resolves the two non-blocking v1 issues: the left card now renders honest Google Place metadata/attributes/description/supporting-info (each gated on a datum actually returned) and the PM2.5 block gains the `Current status` label derived from the existing severity band.

Watch for: nothing blocking. The geocoding fix is correct on both paths and genuinely tested (the new test proves import without a pre-seeded namespace Geocoder — **confirmed**); the map-click reverse-geocode path is behaviorally exercised only indirectly via the init-import assertion, not a click→geocode assertion (**confirmed**, minor coverage note). Heatmap wiring is untouched by both commits and no fakery was introduced (**confirmed**).

## High-level view

The geocoding defect is fixed at both call sites that actually depend on a `Geocoder`. The init effect now `await imp('geocoding')` and constructs `Geocoder` as `(geocodingLib)?.Geocoder || legacy.Geocoder`, so `geocoder.current` — used by the map-click reverse-geocode path — is built from the imported library rather than a namespace that is empty under the async loader. The search fallback no longer reaches into `google.maps.Geocoder` directly; it calls a new `ensureGeocoder()` helper that mirrors `ensurePlacesLibrary`, importing `geocoding` on demand and caching into `geocoder.current`. Honest degradation is preserved: both imports sit behind the existing `MAPS_KEY` guards (init returns early when `!MAPS_KEY`, `runSearch` returns early when `!MAPS_KEY`), so there is no unconditional `importLibrary`.

Error surfacing is now honest without being alarming. Any geocode status other than `OK`/`ZERO_RESULTS` (`REQUEST_DENIED`, `OVER_QUERY_LIMIT`, etc.) raises the existing `unavailable` search status, which is styled amber `#6e4a18` with a Retry affordance — no red. `ZERO_RESULTS` still maps to the benign `no-results` message, and the map-click path stays silent-on-failure as before.

The test gap the user called out is closed with a behavioral test, not a seeded pass. The stub now records every imported library name and only seeds the namespace `Geocoder` when `seedNamespaceGeocoder` is true; the new test runs with it false, asserts `google.maps.Geocoder` is `undefined`, and asserts `'geocoding'` is among the imported libraries and that the fallback still resolves a result through the imported Geocoder. A separate test drives `REQUEST_DENIED` and asserts the amber error status with a Retry button. All three would fail if the fix were reverted.

The left-card metadata is honest. The extra Place fields (`types`, `primaryTypeDisplayName`, `rating`, `userRatingCount`, `websiteURI`, `regularOpeningHours`, `editorialSummary`) are appended to `fetchFields` only on the existing keyed select and map-click paths, and `metaFromGooglePlace` writes each to state only when genuinely present (finite numbers, non-empty strings, real booleans). Every left-card line is conditionally rendered, and a metadata-absent test asserts the facts/attributes/description blocks do not render when Google returns nothing.

The PM2.5 `Current status` word is derived from the existing severity band via `statusWord(sev)` (good→Clean, sat→Acceptable, mod→Elevated, poor→High, worst→Hazardous) — not a new scale — and the test pins AQI 168 → Moderate → `Elevated`.

No hard constraint regressed: no red, Google Place Photo attribution figcaption + contributor link still render (req-06), markup stays inline for styled-jsx scope, `MAPS_KEY` is read only from `process.env.NEXT_PUBLIC_GOOGLE_MAPS_KEY`, the hero `src/pages/vayulok/index.tsx` is unchanged, and the heatmap tiles/opacity are not touched by either commit (no fake gradient / CSS heat colors / dummy heatmap).

### Geocoding init: Geocoder now comes from the imported library on both paths

The init effect adds `const geocodingLib = await imp('geocoding')` and builds `Geocoder: (geocodingLib)?.Geocoder || legacy.Geocoder`. Because `geocoder.current` is constructed from this `maps.Geocoder` later in init, the map-click reverse-geocode path (`geocoder.current.geocode({location})`) now gets a real Geocoder under the async loader, with `legacy.Geocoder` retained only as a fallback for an older loader that already populated the namespace. `imp()` swallows import failures to null, so a `geocoding` import failure degrades to `legacy.Geocoder || undefined` rather than throwing — the same honest-degradation posture the rest of init uses.

The search fallback previously did `if (!geocoder.current && w.google?.maps?.Geocoder) new w.google.maps.Geocoder()` — exactly the namespace dependence that fails in a real browser. That block is replaced by `const gc = await ensureGeocoder()`, where `ensureGeocoder` prefers `importLibrary('geocoding')` and only falls back to `w.google?.maps?.Geocoder` for a legacy loader, caching into `geocoder.current`. Both the sole map-click dependence and the sole search-fallback dependence on a pre-seeded namespace are removed.

Both imports remain behind keyed guards — init is under `if (!MAPS_KEY) return;` and `runSearch` returns early when `!MAPS_KEY` — so no `geocoding` import happens without the existing key/user-action gating.

### Error surfacing: non-ZERO_RESULTS statuses reach the amber unavailable status

The geocode callback now branches: `status === 'ZERO_RESULTS'` keeps the benign `no-results` message, every other non-`OK` status sets `searchStatus('unavailable')`. That status renders `.vl-live-search-status.vl-live-search-status-error`, colored `#6e4a18` (amber) with a lime-green underlined Retry button — confirmed in the styled-jsx block (`.vl-live-search-status-error{color:#6e4a18}`), so the "no red" constraint holds while the failure is no longer swallowed.

### Geocoding test proves the import without a seeded namespace

```js
const rec = installGoogleMaps( { seedNamespaceGeocoder: false } );
expect( window.google?.maps?.Geocoder ).toBeUndefined();   // no namespace mask
...
await waitFor( () => expect( rec.importedLibraries ).toContain( 'geocoding' ) );
```

This is the crux of closing the user-flagged test gap: with the namespace Geocoder absent, the only way the component can later geocode is by importing `geocoding`. The fallback test (also `seedNamespaceGeocoder: false`, `AutocompleteSuggestion` deleted) asserts `rec.geocodeCalls` grows with an India-restricted address request and a selectable Mumbai option appears — which can only happen through the imported Geocoder. Reverting the fix (back to `legacy.Geocoder`) leaves `geocoder.current` null, no geocode call fires, and both tests fail. These are behavioral, not seeded-to-pass.

### Left-card metadata is honest and keyed

`metaFromGooglePlace` is the honesty gate: `Number.isFinite` for rating/count, non-empty-string checks for website/summary, `typeof === 'boolean'` for openNow, and `humanisePlaceType` to turn `tourist_attraction` enums into `Tourist Attraction` prose (deduped, capped at 3). The render tree gates the whole `.vl-live-place-meta` block on `placeMeta.length || placeAttributes.length || summary || supportingInfo.length`, and each sub-block on its own array/value. `PLACE_META_FIELDS` is appended to `fetchFields` only on the keyed select path and the map-click Place-enrichment path, never unconditionally.

The two tests bracket this correctly: the present-metadata test asserts the fields were requested (`rec.placeFetchFields[0]` contains the extra fields), the facts/attributes/description render with real values, and `1,234` formats via `en-IN`; the absent-metadata test selects a place with no metadata and asserts `.vl-live-place-facts`/`-attrs`/`-desc` are all null while the place name still updates — proving no placeholder leaks.
