# VayuLok two-column final-target restructure (v1)

Reshapes `VayuLokLive` into the FINAL TARGET layout: the left column now leads with a selected-place card (relocated photo gallery + number-only lime pill + place name + address), and the air-quality result moves inside that card when a heatmap layer is active. The right column is stripped to map-only: centered search, an AQI|PM2.5 selector, a single marker, and Google attribution. The Expand/Collapse control, the floating on-map photo overlay, and the on-map legend are gone. The req-05 "flatten tiles to one lime" treatment is reversed per the owner's new instruction — tiles keep their scientific value variation at ~30% opacity, and lime #d1f470 now lives only on the selector chrome. All markup stays inline in the return tree, so styled-jsx scope holds.

Watch for: the left place card renders only name + address + the environmental result — the spec's "metadata / attributes / description / supporting information" lines are not implemented (confirmed). The PM2.5 block omits the explicit "Current status" label the mockup shows (confirmed, minor). No red is introduced and attribution/key safety are intact (confirmed).

**Verdict**: APPROVED

## High-level view

The heatmap conflict is resolved the way the owner's latest instruction demands: `HEATMAP_OPACITY` drops 0.35 → 0.30, the hue-collapsing CSS filter and its runtime `vl-live-overlay-lime` class are deleted, and the only remaining client-side treatment is translucency. `UAQI_RED_GREEN` is deliberately retained for AQI tiles because preserving value variation was ranked above a flat lime; this is a defensible reading of the spec and the trade-off is documented in the task findings. No new red color literals enter the diff.

The map is correctly reduced to the five allowed elements. The `mapExpanded` state, the `is-expanded` stage sizing, and the Expand/Collapse button are removed together, and the layer buttons now toggle off on re-click. The active selector tab is filled with the exact `--lime` (#d1f470) and `#1a3a2a` text/border, replacing the earlier approximate translucent lime.

The photo gallery and number-only pill relocate cleanly into the left card, carrying the Place Photo author-attribution figcaption and contributor link with them, so the req-06 guard still holds. Photo cells now share the exact pill lime (#d1f470) instead of the lighter `--lime-solid`, which is deleted.

Honest degradation is preserved: the live NOW block and map stay gated on a key, and search->select updates both columns from the same `place` state. The gap against the spec is in the left-card body: it stops at name + address + the layer-gated result, with none of the metadata/attribute/description/supporting-info content the FINAL TARGET diagram sketches for the default state.

### Heatmap conflict resolution: translucency over recolour

The previous cycle baked Google's multi-hue AQI ramp toward a single lime via a scoped CSS filter plus a runtime `vl-live-overlay-lime` class on the canvas host. FINAL TARGET reverses that. The filter block and the class toggle are both deleted, so the overlay effect's cleanup is now a plain `map.overlayMapTypes?.clear()`, and the tiles render with their native colormap at `opacity: 0.30` (set via both the `ImageMapType` constructor option and `setOpacity`). The outcome matches the owner's instruction: road geometry and labels read through, and the scientific gradient survives rather than collapsing to a flat wash (confirmed).

Retaining the `UAQI_RED_GREEN` enum for AQI is the one spot where "no red" and "preserve variation" pull against each other. The enum name references a server-rendered raster colormap, not a page color token, and the user explicitly prioritized value variation over flattening. Keeping it (and documenting the trade-off in `FEAT-002.json`) is a reasonable reading of the spec rather than a palette violation (likely — the actual rendered raster can't be inspected in-sandbox because the key is referrer-restricted, which is expected). PM2.5 keeps `PM25_INDIGO_PERSIAN`. The overlay is still created only when `layer` is non-null, so no heatmap or tile fetch happens on load, and switching layers clears before pushing so overlays don't accumulate (confirmed).

### Photo + pill relocation and attribution survival

The photo shell, the number-only pill (`.vl-live-photo-count`: referee SVG + bare integer, aria-label `"{n} place photos"` but no visible "photos" text), and the attribution figcaption all move from the `.vl-live-map-photos` on-map overlay into `.vl-live-place-card` at the top of the left column; the overlay container and its tab rail are deleted. The `.vl-live-photo-credit` figcaption with its contributor `<a href>` moves intact, so the req-06 guard still has something to assert against in the left column. Photo cells switch from `--lime-solid` (#f5fde0) to `--lime` (#d1f470) so pill and photo backdrop share one lime, and `--lime-solid` is removed from the token block (confirmed). No rule targets `.gm-style-cc`, `a[href*="google"]`, or `img[alt="Google"]`.

### Left-card content stops short of the spec

The card body is `place.name`, `place.addr`, and — when `liveActive && layer && air` — the environmental result. The FINAL TARGET default-state diagram also lists "Real place metadata", a "✓ Relevant attribute" checklist, a "Useful place description", and "• Supporting information" bullets. None of those render in the card (confirmed: the body is two `<p>` elements plus the layer-gated result). The place fetch pulls only `displayName`, `formattedAddress`, `location`, `photos`, so the data for metadata/attributes/description isn't being requested either.

This is a spec-fidelity gap, not a functional break: the broader left column below the card still carries the full existing VayuLok content (air/weather NOW, pollen, solar, plan), and the spec's own wording hedges ("Real place metadata *when available*"). But the dedicated place-card body the diagrams center on is thinner than drawn. Worth an explicit decision: either populate it (which needs more Place fields and new markup) or ratify name+address as the intended card body and amend the spec. The PM2.5 result block has a smaller version of the same issue — it leads with the PM2.5 reading and AQI band but omits the explicit "Current status / Elevated" label from the mockup, conveying status only through the severity dot and band word.

### Search updates both columns from one state

The `choose` flow (unchanged by this cycle) resolves the selected prediction via `fetchFields`, writes `place`, clears any map-click candidate, and the recenter effect moves the single marker — so one selection drives the left card (name/address/photos via `previewPlace`) and the map together. Under FINAL TARGET the left card *wants* the photos, so the earlier concern that search "still fetches photos" is inverted here: fetching photos on select is now correct, because they populate the left card. India autocomplete scoping (`includedRegionCodes:['in']`, session token, India bounds) is untouched.

### Tests meaningfully track the restructure

The replaced tests assert behavior that would regress if the restructure were undone rather than static values. The expand-control test is inverted to assert `Expand map`/`Collapse map` buttons and `.vl-live-map-expand`/`.is-expanded` are *absent* while `gestureHandling:'greedy'` stays. A new test stubs a real AQI air response, clicks AQI, and checks the result block appears *inside `.vl-live-left`* with the AQI value, category word, and "Air quality now", then clicks PM2.5 and checks the block swaps to "PM2.5 heatmap result" with the PM2.5 figure — this exercises the actual layer->left-card wiring, not a mock. The photo-overlay test drives search->select and asserts the pill is number-only (`/^\d+$/`, not matching `/photo/i`), lives under `.vl-live-left`, and that `.vl-live-map-photos` and any `.vl-live-right .vl-live-photo-count` are gone.

Not tested: that the active selector tab actually renders `#d1f470` (the exact-lime requirement is asserted only by reading CSS, not in a test), that `HEATMAP_OPACITY` is translucent via the `ImageMapType` option (the task notes claim an opacity assertion but the visible diff asserts enum values and overlay presence, not the numeric opacity), and the left-card metadata/attributes block (which doesn't exist, so there's nothing to cover).
