# Checkout handoff: exact pricing, durable quarantine, website Razorpay path, backend session (v1)

Four commits (`99eed12`..`5a1f043`) land the AWS-independent half of the WECARE.DIGITAL checkout handoff: a single exact convenience-fee + GST-on-fee calculator with an immutable quote snapshot (section 7), durable capture-quarantine and bound/idempotent wallet top-ups in the Razorpay webhook (section 5 R3/N3/N2), the website Razorpay Standard Checkout code path behind a disabled initiation gate (section 8), and a backend-owned opaque-cookie customer session plus the seven section-6 sign-in strings and a private Download-receipt (sections 6/9/16). The approach is uniformly "the event body is never money authority": every financial decision is re-derived from an authoritative provider readback or a stored intent, and every new money primitive is a conditional write that is tested against a DynamoDB fake rather than mocked away. The 121481-paise fixture is exact (verified independently), the initiation gate defaults off on both the in-chat and website paths, callback HMAC is computed over the server-stored gateway order id, and the merged `#175` divided phone field, bag control and PageTopBand shell are untouched.

**Watch for:** the website callback verifies stored amount/currency but does not read back the stored `accountMode`/`accountKeyId` the binding persists expressly to stop a test-mode success settling a live-mode order (possible); and the retained in-chat `PAYMENT_REQUEST_SENT` response coexisting with the new website contract is a deliberate owner decision, not a regression (confirmed, informational).

**Verdict**: APPROVED

## High-level view

The pricing calculator is the one place the convenience fee and its GST are computed, in integer paise with `Decimal`/`ROUND_HALF_UP` and no float anywhere on the path; floats, bools and fractional-paise Decimals are rejected rather than rounded, and the 121481-paise fixture reconciles exactly. The quote freezes into an immutable, customer-owned snapshot whose SHA-256 hash changes with any cart/address/amount edit and which refuses to be charged once expired.

The webhook's wallet top-up branch, which the prior findings flagged as crediting unverified event notes ahead of every gate, now credits only through three ordered gates: a stored top-up intent the business created, a provider-verified captured amount equal to that intent, and a conditional idempotency marker claimed before the credit. The amount credited comes from the stored intent, never the event body. Captures that cannot be authoritatively cleared are parked in a durable, idempotent quarantine row that survives past CloudWatch retention and Razorpay's retry window, with a reconciliation script to list and acknowledge them without ever writing financial state.

The website Standard Checkout path is additive and handler-free (every dependency injected), gated by `CHECKOUT_INITIATION_ENABLED` (default off) so turning nothing on creates no payable order. It reserves a customer-scoped request key before any provider call, coordinates concurrent clicks and rejects a changed intent on a resumed key, binds the created gateway order's id/account/mode/amount before exposing browser options, and treats an ambiguous create as a reconciliation state rather than minting a second payable order. The callback verifies the HMAC over the server-stored order id and still requires an authenticated capture readback before any paid state.

The customer session holds Cognito tokens server-side and hands the browser only an opaque id in a `Secure; HttpOnly; SameSite=Lax`, host-only cookie; the row is keyed by a hash of the id, idle and absolute deadlines are enforced server-side on every validation, a successful refresh slides idle but never the absolute anchor, and refresh is single-flight so a rotating refresh token is not spent twice. The private receipt is rendered from the frozen paid snapshot, written only under the gated secure root (never the public bag-icon prefix), authorised against the session with cross-customer denial, and keyed deterministically for idempotent regeneration. The seven section-6 strings live in one shared module the sign-in page references and a test pins verbatim, with no red validation treatment.

### Exact paise arithmetic and the 121481 fixture

`checkout_pricing.compute_quote` is the single calculator, and the formula is integer basis points over a 10000 denominator evaluated in `Decimal` with `ROUND_HALF_UP`: `fee = round_half_up(collection * 250/10000)`, `gst = round_half_up(fee * 1800/10000)`, `total = collection + fee + gst`. On the mandated input (118000 paise) this is `fee 2950`, `gst 531`, `total 121481`, which reconciles exactly — confirmed by re-deriving it outside the module. There is no float on the path by construction: `_validate_collection_paise` rejects floats, bools and fractional-paise Decimals rather than rounding them, and `_canonical` refuses a float or fractional Decimal in the snapshot payload so a bad value cannot silently poison the hash. The odd-paise GST split floors SGST (265) and gives the remainder to CGST (266), and the split is re-checked to sum back to 531.

The reconciliation `total == collection + fee + gst` is re-asserted in `__post_init__`, so a hand-constructed instance cannot violate it. The snapshot hash covers customer, cart id+revision, item list, address, delivery and the rounded components, and a quantity, address or amount change each moves it; `is_expired` refuses a charge at or past the absolute expiry; and a zero-total quote has `is_payable` false with `as_payable_money()` raising, so an uncharged order can never reach the gateway.

### Wallet top-up: stored intent, provider readback, idempotency

This is the defect the prior findings called the highest risk — crediting `partner_billing.topup` directly from `payment.notes` ahead of verification. `_handle_wallet_topup_captured` now gates in order: resolve a `TOPUPINTENT#` row the customer-service flow reserved before the payment link existed (no intent → quarantine, credit nothing); reject a WABA in the event that differs from the stored intent's; verify the captured amount against Razorpay's API and require it equal the intent to the paise; then claim a conditional `TOPUPCREDIT#<paymentId>` marker before crediting. The credited figure is `Decimal(intent_paise)/100`, from the stored intent, never the event body.

The tests drive the real handler against the DynamoDB fake and prove the behaviours that matter: a forged event inflated to 10× the intent still credits only the provider-verified intent amount (`₹500.00`, exact); a duplicate delivery credits exactly once and leaves a durable credit marker; a provider amount mismatch, a not-captured verdict, and a missing intent each credit nothing and park the capture. The intent is reserved on the initiation side in `partner-onboarding/_do_topup_order`, which allocates a payment reference and writes the intent before building the Razorpay payment link, carrying the `referenceId` through the notes so the webhook can bind to it.

### Durable capture quarantine

`_quarantine_unverified_capture` previously emitted a staff alert log and nothing else, which disappears once CloudWatch retention lapses and is gone entirely once Razorpay stops retrying. It now writes a durable `CAPTUREQUARANTINE#<paymentId>` row via the same conditional-write primitive order creation uses, keyed by payment id and idempotent so a redelivery updates nothing and does not reset `createdAt` or an acknowledgement. It writes nothing financial. A storage failure is surfaced (logged by type) but does not fail the webhook, because a non-2xx would make Razorpay retry the whole event and the dedup lease already handles recovery. `scripts/reconcile_captures.py` scans the namespace, reports, and acknowledges rows without ever writing financial state; acknowledgement records that a human saw the row and deliberately does not delete it, so it stays recoverable.

### Website Razorpay path: gate, binding, callback

`prepare_checkout` runs every guard before any provider call — ownership, the presented snapshot hash `matches()`, not expired, INR, and the amount is the calculator total via `as_payable_money()` — and reserves a customer-scoped request key before the external call so a resumed key with a changed intent fingerprint is rejected rather than charged. With the gate off (default) it returns `PAYMENT_INITIATION_DISABLED` with no gateway order and no payable attempt. The binding (`GATEWAYORDER#`, carrying id/account/mode/amount/currency) is persisted before `_browser_options` exposes anything, and the browser projection is exactly `keyId` (public), `orderId` (stored gateway order id), `amountPaise`, `currency`, a restricted prefill and the attempt id — no secret, no raw Wix total.

An ambiguous create (timeout, or a create that may have landed but whose binding could not be saved) never mints a second payable order: `razorpay_orders.create_order` raises `RazorpayUnavailable` on any transport/HTTP error, and the recovery path correlates by the self-minted receipt via `find_order_by_receipt`, binding to the landed order if found and otherwise reporting `CHECKOUT_AMBIGUOUS`. `create_order` forces `partial_payment=False` so a customer cannot pay a fraction of the reviewed total.

`verify_callback` resolves the binding by the stored gateway order id (an unknown id is a mismatch), computes the HMAC over the stored order id — never the browser's `presented_order_id` — using `hmac.compare_digest`, and treats a valid signature as only a trigger: it still requires `verify_capture` to confirm an authenticated capture and the captured amount/currency to equal the binding before `VERIFIED_PAID`.

One gap: the binding stores `accountMode` and `accountKeyId`, and the `account_mode`/`bind_gateway_order` docstrings state the mode exists so "a test-mode success must never settle a live-mode order," but `verify_callback` reads back only `amountPaise` and `currency`, not the mode or account. The signature is keyed with a single account's `key_secret`, so a cross-mode settle would also need a cross-mode-valid signature, which makes this likely unreachable in practice — but the stored field that was added to enforce the invariant is not consulted on the path that would enforce it. Worth either wiring the check or recording why the signature alone is considered sufficient.

### Razorpay order-create and signature module

`razorpay_orders` reads `wecare/razorpay/api` (`key_id` + `key_secret`), explicitly not the webhook secret, lazily and cached per sandbox for the documented SnapStart reason. `key_secret` is used only as basic auth and the HMAC key and never leaves the module; `public_key_id()` exposes only the publishable id. No value is ever logged — error paths raise `RazorpayUnavailable` with HTTP status or exception type only, because Razorpay error bodies echo the request that carried basic auth. `verify_checkout_signature` fails closed on a missing field or an unavailable secret. The HMAC uses the `order_id|payment_id` string Razorpay documents, keyed with `key_secret`, over the caller-supplied (server-stored) order id.

### Backend-owned customer session

Tokens stay server-side; the browser gets an opaque 256-bit id in a `Secure; HttpOnly; SameSite=Lax`, host-only cookie, and the row is keyed by `sha256(id)` so a table read yields hashes, never usable ids. Idle (7-day) and absolute (30-day persistent / 12-hour shared-device) deadlines are checked against the stored row on every `validate`, so a replayed cookie past either deadline is refused regardless of the browser's `Max-Age`. A successful `refresh_access_token` slides the idle deadline and may replace the refresh reference but never touches `absoluteExpiresAt`, which is anchored to `createdAt` — the section-16 "a refresh must not extend the absolute deadline" rule, enforced in code. Refresh is single-flight via a conditional claim on `refreshInFlight` with a bounded lease and bounded retries, so a rotating single-use refresh token is not spent twice; a transient provider fault raises `RefreshUnavailable` (503, session kept) while only a definite `RefreshFailed` revokes. `rotate` swaps the id on sign-in without resetting the absolute anchor, `revoke` is idempotent, and CSRF is a per-session double-submit token compared in constant time.

### Private Download-receipt

`generate_receipt` authorises first — `authorize_resource` checks the snapshot's `customerId` against the proven identity, and a cross-customer snapshot is refused with the same opaque result as a missing one, so the endpoint is not an existence oracle. The storage key is derived from the snapshot hash and format and passed through `assert_private_key`, which refuses any key outside the gated secure root and specifically the public bag-icon prefix, so a careless edit cannot re-publish a receipt that carries a name, address and GSTIN. Amounts come straight from the frozen snapshot's integer-paise components converted to rupees (the only arithmetic), so the printed total equals the charged total, and the key derivation makes regeneration idempotent. The signed URL is bounded by `receipt_links` and never logged.

### Section-6 strings and preserved UI

The seven approved strings live in `src/lib/signInMessages.ts` and `SECTION_6_MESSAGES` equals the owner's table in order and count; the sign-in page references the constants instead of re-typing them, and the test pins both the array and each named constant verbatim and asserts the reachable error states render an approved string with no red inline or block colour. `MISSING_CODE` and `NOT_ON_WHATSAPP` are present as auditable constants but deliberately not wired to a reachable state (the divided `#175` phone field always carries a dial code, and the only backend send-failure signal cannot distinguish "not on WhatsApp" from a transient Meta outage); `NOT_ON_WHATSAPP` is explicitly excluded from the seven. The cart and sign-in diffs are documentation and a sourcing change only — the divided phone field, bag control and PageTopBand shell are untouched.

### Test coverage

The 111 new tests across the five suites pass and exercise real code: the pricing suite asserts exact arithmetic and the refusal paths; the quarantine/wallet suite drives the real webhook handler against an honest DynamoDB fake so the conditional writes are evaluated for real, forging inflated and misdirected event bodies; the website suite drives `prepare_checkout`/`verify_callback` with the real conditional-write store and a mocked provider; the session suite drives single-flight, idle/absolute expiry and both refresh failure modes; the receipt suite drives authorisation, private-key enforcement and idempotent regeneration against a mocked S3. These would fail if the implementations were reverted — they assert behaviour (event-body cannot select a payment, duplicate credits once, expired snapshot cannot be charged), not static values.

Not tested here (and correctly out of scope / blocked): the live `razorpay_verify` provider readback that both new money paths depend on is unchanged and assumed-correct; all AWS deploy, Cognito app-client inspection, S3 upload and live-provider verification steps are recorded BLOCKED-ON-ENVIRONMENT and delivered as source + injected-dependency tests, not faked as done.
