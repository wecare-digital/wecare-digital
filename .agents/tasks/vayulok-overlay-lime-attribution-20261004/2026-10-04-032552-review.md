# Lime-translucent AQI/PM2.5 heatmap recolor and preserved Place-photo attribution (v1)

This cycle takes the VayuLok live page's AQI/PM2.5 heatmap overlay — a `google.maps.ImageMapType` built only on a layer-button click — and makes it both lime-tinted and genuinely see-through so the geo/road map underneath stays readable (req 05), and it resolves the "remove all attribution/EXIF" ask down to the legally permissible subset: it keeps Google's mandated Place-photo author attribution and map logo/legal intact, documents that no project-owned EXIF pipeline exists, and adds a guard test (req 06). Translucency is driven two ways — a low `ImageMapType` opacity (0.35) plus `setOpacity`, and a CSS filter/blend/opacity chain scoped to the overlay tile images — while the lime recolor is a scoped filter that collapses Google's baked multi-hue ramp toward `--lime` and removes red. The previously orphaned heatmap legend is restored inline, shown only while a layer is active, reusing the no-red `--aqi-*` ramp with both ends labelled in words. The active layer button was moved from an approximate `rgba(209,244,112,.72)` to the exact `--lime` token.

Watch for: (1) **confirmed** — the recolor selector `.vl-live-overlay-lime :global(div[style*="z-index"] img:not([alt]))` is scoped by a runtime-added class on the map canvas, not by `.vl-live-map-stage` as its own comment claims; the scoping still works, but the comment is misleading. (2) **possible** — because the selector lives on the map-canvas ancestor and matches any alt-less `<img>` inside a z-indexed pane, Google's own base-map raster tiles (also alt-less) can receive the same lime filter, not just the overlay pane; this is a fidelity nuance, not a ToS break. (3) **confirmed** — no automated test can verify the lime pixels or that base-map tiles are spared, since the key is referrer-restricted; the recolor rests entirely on untested CSS.

**Verdict**: APPROVED

## High-level view

The lime+translucent treatment is split deliberately: opacity is handled through the Maps API surface (constructor `opacity` and `setOpacity`), while hue is handled by a client-side CSS filter chain, because the tiles are server-baked rasters with no color parameter — the research doc (Option B) justifies this as the only path that delivers translucent + lime + no-red + zero added billing without a custom tile renderer. The honesty of that doc is a strength: it states plainly that a filter cannot pin every pixel to exactly `#d1f470` and names Option D as the future pixel-exact path.

The ToS-sensitive part — not recoloring or hiding Google's logo, legal, or photo attribution — is handled by two guards working together: the filter selector only matches alt-less `<img>` tiles (Google's attribution image carries an alt), and the legend is inset from the map's bottom corners where Google paints its logo. No new CSS targets `.gm-style-cc`, `a[href*="google"]`, or `img[alt="Google"]`. The place-card photos are rendered *with* an alt, so they are also outside the recolor's reach — correct, if slightly incidental.

Req 06 is bounded exactly as the briefing describes and should not be read as an unmet requirement: the mandated Place-photo author attribution stays, no attribution-hiding CSS was added, and the EXIF finding is accurate — the repo has no raster/EXIF pipeline and Place Photos are live-fetched URLs, so there are no raw bytes to strip. A guard test now fails loudly if the attribution figcaption or its contributor link ever disappears.

The gaps are all in verifiability rather than correctness: the one thing a reviewer cannot confirm here is that the lime filter lands on the overlay pane *only* and that the resulting wash is actually legible over the road map, because neither renders in CI.

### Opacity through the API, hue through CSS

The split follows from the constraint the research doc establishes: the heatmap tiles are rasters rendered server-side with a fixed colormap and no color/tint parameter, so "same lime as the site" cannot come from the endpoint. Translucency uses the `ImageMapType` constructor `opacity: 0.35` plus a defensive `setOpacity?.(0.35)`; the unit test asserts a numeric opacity strictly between 0 and 1 rather than pinning a brittle value. Hue is a separate CSS concern on the painted tile `<img>`s:

```css
.vl-live-overlay-lime :global(div[style*="z-index"] img:not([alt])){
  filter:grayscale(1) brightness(1.08) sepia(0.72) hue-rotate(32deg) saturate(2.1) brightness(1.06) !important;
  mix-blend-mode:multiply;
  opacity:.72;
}
```

The `.72` CSS opacity compounds with the `0.35` ImageMapType opacity, so the effective overlay alpha is well under half, satisfying "fully translucent." The research doc is candid that the filter chain unifies toward lime and kills red rather than hitting exact `#d1f470`, so the trade-off is auditable.

### Scope story: works, but the comment lies about how

The lime treatment is reached by `mapHost.current.classList.add('vl-live-overlay-lime')` inside the heatmap effect, with a cleanup that removes it when `layer` clears. `mapHost` is the `.vl-live-map-canvas` div, written in the JSX return tree, so styled-jsx stamps its scope attribute onto that element at render time; when the runtime class is added the element carries both, so the compiled scoped selector matches. The runtime-added class is the kind of thing that silently defeats styled-jsx scoping, so it is worth confirming it does not here.

The misleading part is the prose around it. The effect comment says "see `.vl-live-map-stage .vl-live-overlay-lime` below," and the CSS block comment repeats "scoped to the overlay tile pane only (see `.vl-live-map-stage .vl-live-overlay-lime`)." The actual selector has no `.vl-live-map-stage` ancestor — the scope is the canvas node alone. The code is right; the comments describe a selector that was never shipped and should be corrected so a future maintainer trusts them.

### What the filter actually matches

The `:not([alt])` guard is the ToS firewall and it is sound: Google renders overlay heatmap tiles as plain alt-less `<img>`s, while its attribution/logo image carries alt text, so the recolor can never touch the logo. The place-card photos also carry an `alt` (`"${previewPlace.name} area N"`), so they are outside the selector too — a useful side effect, though it depends on those photos always having an alt.

The looser edge is the ancestor. The selector hangs off `.vl-live-overlay-lime`, which is the whole map canvas, and matches any alt-less `<img>` inside a `div[style*="z-index"]` under it. Google's base-map raster tiles are also alt-less `<img>`s inside z-indexed panes under that same canvas, so the lime filter can land on them as well as on the overlay tiles. Functionally this is not a ToS problem — the logo is alt-tagged and spared, and a lime-tinted base map still shows roads — but it is not the "overlay tile pane ONLY" the comments promise, and it could make the base map read greener than intended. Worth a live check; if confirmed, narrow the selector to the overlay pane specifically. This cannot be settled in CI because the stub does not model Google's DOM panes.

### Restored legend, kept inline and inset

The legend is rendered inline in the return tree, gated on `layer`, so styled-jsx keeps its scope and it appears/disappears with the overlay. It reuses the `--aqi-*` ramp — `#1a3a2a → #3da35a → #d1f470 → #e8c547 → #c98a2e`, dark green to lime to amber, no red — and labels both ends "Good"/"Hazardous" in words so color is not the sole carrier. The container is pinned bottom-left with a 16px inset and bounded width, keeping it off Google's bottom-corner logo/legal. The new test confirms it is absent on load, appears on AQI activation, and carries exactly the two word-labels.

### Req 06: attribution kept, EXIF finding accurate

The bounded interpretation is correct and intentional. Nothing in the diff hides attribution: no CSS targets `.gm-style-cc`, `a[href*="google"]`, or `img[alt="Google"]`, the `.vl-live-photo-credit` figcaption and its `credit.uri` links are untouched, and the overlay/legend stay inset from the logo corners. The EXIF finding holds up against the code — the only image path forwards the user's `File`/`Blob` as-is with no re-encode, and Place Photos are live `getURI` URLs the app never holds as bytes, so there is genuinely no local EXIF to strip and no dependency was added.

The guard test is the right shape: it feeds a Place photo with non-empty `authorAttributions` through the real search→select flow and asserts the figcaption renders with the contributor's name and a link to the Google `contrib` URI with `target=_blank`. That locks in the mandated attribution against accidental future removal, which is more valuable than asserting the attribution's styling.

### Preserved behavior

The hard constraints the briefing flagged all hold against the diff: the overlay is still built on-layer-click only (clear, early-return on no `layer`, construct after a layer is chosen); the enums stay `UAQI_RED_GREEN`/`PM25_INDIGO_PERSIAN` with a test asserting PM2.5 is not the invalid `PM25_HEATMAP`; the key is read only from `process.env.NEXT_PUBLIC_GOOGLE_MAPS_KEY` with no literal in source; and the no-key degradation test (no map, zero fetches) still passes. The active layer button moved to the exact `--lime` token while the unrelated expand toggle was deliberately left on the approximate lime — scoping the exact-lime change to req 05, as the owner intended.
