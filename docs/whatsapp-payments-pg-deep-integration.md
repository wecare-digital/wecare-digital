# WhatsApp Payments — Razorpay PG Deep Integration (Path A), authoritative reference

Source: Meta WhatsApp Business Payments API (India), fetched 2026-10-02. This is the
build contract for native in-chat WhatsApp payments. It supersedes the 2026-10-01
"website-only" ruling for the WhatsApp channel, by owner decision 2026-10-02.

## The channel model (owner, 2026-10-02)

Website and WhatsApp are two **channels** over **one shared backend**. Shared: Wix
products (one catalogue), blogs, coupons, the order table, the customer table +
records + management, and the order pages. The **only** per-channel difference is the
payment surface:

| Channel | Payment surface | Same account? |
|---|---|---|
| Website | Razorpay web checkout (existing) | Razorpay merchant `wecare` |
| WhatsApp | Razorpay via Meta PG Deep Integration (`order_details`) | **same** Razorpay merchant, surfaced to Meta via a payment configuration on the WABA |

Same Razorpay key, same webhook, same reconciliation, same settlement. Meta is only
the surface. A WhatsApp order is a normal order in the same table, tagged
`channel=whatsapp` (Phase W FEAT-002 built the channel spine). Same customer (keyed by
E.164 phone), same order pages.

## Full feature set to build (so "all features are in place")

### 1. Send: `order_details` interactive message (Step 1)
- `action.name = "review_and_pay"`, `parameters` is a **stringified JSON object**.
- `payment_settings[0].type = "payment_gateway"`,
  `payment_gateway.type = "razorpay"`, `configuration_name = <published name>`.
- Razorpay UDF: `receipt` (<=40 chars, our WD order number) and `notes` (<=15 keys,
  <=256 chars each) carried through to payment signals — use for correlation.
- `reference_id`: unique, <=35 chars, `[A-Za-z0-9._-]`, generated by us
  (`REFERENCE#<metaReferenceId>` resolve-before-generate — steering
  whatsapp-payments-india-reference). Stable across retries; add `-<seq>` for repeats.
- `currency = INR`, `total_amount.offset = 100`, integer paise only (no float).
  `total_amount.value == subtotal + tax + shipping - discount` (enforce, fail closed).
- `type`: `physical-goods` (needs `beneficiaries` for shipping) or `digital-goods`.
- Catalog mode: `order.catalog_id` + `items[].retailer_id` (our
  `wix:<productId>:<variantId>` from meta_catalog_sync). Non-catalog mode: items need
  `country_of_origin`, `importer_name`, `importer_address`.
- `order.status = "pending"` (only allowed value on send). Optional `expiration`
  (min 300s). Optional `order.type = "quick_pay"` to show only "Pay Now".

### 2. Order details **template** message (out-of-window)
- UTILITY template with a fixed `ORDER_DETAILS` button ("Review and Pay"). Owner creates
  + gets approved. `WA_PAY_TEMPLATE = wecare_pay` already reserved in manifest.
- Lets us send a pay prompt outside the 24h window. Carries the same `order_details`
  action payload in the button component.

### 3. Receive: payment status **webhook** (Step 4)
- `statuses[].type = "payment"`, `status` ∈ `captured|pending|failed`.
- `payment.transaction.{id, pg_transaction_id, type=razorpay, status, method, error}`,
  `payment.{amount, currency, receipt, notes, refunds[]}`.
- **Never trust the webhook alone** (security requirement). It is a trigger to look up.
- Route every status decision through `lambda_utils/payment_status.py` (monotonic,
  the `captured` literal is AST-banned at decision sites). Replay-safe on `reference_id`.

### 4. Confirm: payment **lookup API** (Step 5) — mandatory
- `GET <PHONE_NUMBER_ID>/payments/<PAYMENT_CONFIGURATION>/<REFERENCE_ID>`.
- Response `status` ∈ `pending|captured`; `transactions[]` present once attempted; at
  most one `success`. This is the source of truth, not the webhook.

### 5. Order status updates (Step 6) — mandatory after any transaction update
- `interactive.type = "order_status"`, `action.name = "review_order"`.
- `status` ∈ `pending|processing|partially_shipped|shipped|completed|canceled`.
- Transition rules: `pending` → any; `processing/shipped/partially_shipped` interchange
  or → terminal; `completed`/`canceled` terminal. Errors `2046` (bad transition),
  `2047` (cannot cancel a paid order). The order page in-chat only reflects
  `order_status` messages, so one MUST be sent after every PG transaction update.

### 6. Refunds (Step 8)
- `POST /[PHONE_NUMBER_ID]/payments_refund` with `reference_id`, `speed`
  (`instant|normal`), `payment_config_id`, `amount{currency,value,offset}`.
- Guarded by standing refusal: payment capture/refund/config mutation is PROHIBITED for
  the agent — build the code path + tests, but the live refund call is owner-only. Flag
  default OFF.

### 7. Extras from the spec
- Merchant-preferred UPI app: `preferred_payment_methods[].method` (gpay/phonepe/paytm/
  bhim/amazonpay/cred/mobikwik).
- Restrict options: `enabled_payment_options = ["upi"]` or `["web"]`. UPI capped at
  ₹5,00,000 — above that force `["web"]`.
- TPV (Razorpay): `encrypted_payment_gateway_data` (alpha, owner+Meta+Razorpay only).
