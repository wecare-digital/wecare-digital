# Workspace and public-site audit, 7 October 2026

## Scope and evidence

Audited production source `a82ff4c9` on separate branch `codex/workspace-audit-redesign-20261007`. Enumerated all 149 page files: 113 workspace routes and 36 public route patterns, excluding Next's `_app` and `_document` framework files. A dynamic route represents a family of product/post/topic pages, not a count of every generated URL. Traced local imports, API helper calls, object API exports, direct request sites, feature flags, page embedding and navigation registration. Source contains 80 `handler.py` files; that is not an expected deployed-function count because it includes legacy/alternate implementations.

Live AWS discovery verified account 775261844268, us-east-1: 74 Lambda functions, one HTTP API (`zllr9lrg7j`), 374 routes, 74 integration records and 84 DynamoDB tables. Every route's referenced Lambda function exists. Alias discovery and Amplify settings were checked separately. Missing aliases are not automatically defects: several integrations intentionally target unqualified functions. Metadata snapshots contain no credential values or customer records.

This is a complete source-route inventory and targeted backend/configuration review, **not a signed-in end-to-end certification of every screen**. Import reachability includes inactive tabs. Path matches include greedy gateway routes, but do not establish verb parity, handler dispatch, IAM, provider permissions, payload compatibility or successful runtime results. Direct request variables and backend dispatch need manual review. No live customer messages, payment actions, publishing, credential reads or infrastructure changes were performed.

## Backend exists but the workspace lacks an operational surface

1. **Paid service requests — needed.** New service-request lifecycle needs a staff queue, assignment/status history and amendments. Customer `/orders`, `/submit-request` and `/request-amendment` keep customer-only authentication. Staff Contracts and UI are new work.
2. **Failed messages / DLQ — needed for support.** `GET /dlq` and `POST /dlq/replay` exist; helpers are not called by a working queue. Static documentation is not a screen. Add read-only errors first; replay requires idempotency and constrained Operator/Admin action.
3. **CRM pipeline — optional.** Twelve live CRM routes and pipeline/lead/opportunity tables exist. Contact 360 currently aggregates messages, invoices and orders, not `/crm/contacts/{id}/360`. The old public `/crm` route was deliberately removed, with a test enforcing its absence. Do not restore a public CRM page. Add a workspace funnel only if leads/opportunities are part of daily work; otherwise document backend-only status and evaluate usage before retirement.
4. **Notification delivery timeline — useful backend work first.** Worker and event/outbox/attempt/delivery tables exist, but there is no dedicated staff delivery-inspection API family. Build a safe read contract before a UI. Table existence alone does not justify direct browser access.
5. **Partner wallet/ledger — role-scoped need.** Partner billing APIs exist; keep own-account data in Partner account experience. A staff ledger/reconciliation surface needs an explicitly separate contract and role checks. Never merge customer/partner balances into general billing totals.
6. **Agent approvals — already present contextually.** InternalChatTab fetches approvals; improve discoverability in a work queue rather than inventing duplicate approval logic.
7. **Coupons / gift cards — not a current UI gap to fill.** Handler source exists, but current Lambda/route inventory has no corresponding deployed service. Keep deferred pending a business requirement and end-to-end backend readiness.

## Proposed navigation and page decisions

Preserve the short daily sidebar principle. Proposal: **Inbox, Contacts, Campaigns, Service Ops, Payments, Catalog, Tasks**, plus **Content** for authorized editors. Forms/Flow responses become Service Ops queues. Broadcast becomes Campaigns (drafts, audience, schedule, delivery), using existing operational surfaces. Content is a resource workspace for Blog Studio, production batches and supported SEO; it is not provider account configuration.

**Settings** stays a fixed lower control. Organize its panel into Your account; Integrations; Channels; Automation & AI; Platform. Integrations includes MCP and provider connections with precise statuses. Platform is Admin-only. Diagnostics and one-time WABA setup do not compete with customer work. Use local tabs for resource tasks; at most one nested sidebar level. Deep detail routes remain addressable and appear in contextual breadcrumbs and capability-filtered search.

Keep Contacts as canonical list, Contact 360 as selected-contact detail. Keep one invoice ledger and invoice detail; payment composers become actions from customer/order context. Keep product catalog distinct from WhatsApp catalog/Flow mapping, but link the records by provider/product ID. Keep outbound Voice and IVR/Calling settings distinct from voice records in Inbox. Common inbox, messaging analytics and estimated usage are distinct views over related data, not three independent message stores.

Keep legacy redirects `/workspace/admin`, `/workspace/docs`, `/workspace/forms`; remove them from repeated menu destinations. Keep Service Ops and Payments hubs that embed existing components: this is intentional reuse, not duplicate implementation. Extract shared resource components from `src/pages` so hubs no longer import routed page modules. Preserve URL query-selected tabs and Back behavior.

Every page's proposed domain, decision, reason, source API helpers, backend-route evidence, flags and discoverability are in the JSON/CSV/HTML inventory. “Keep” means preserve the capability; it does not certify runtime correctness or require its own permanent standalone menu entry.

## Public pages

All 36 public route patterns are included. Product/Flow landing pages share `ProductPage` intentionally: distinguish their offering, status, primary CTA, eligibility and price. Do not delete them because their JSX is similar. Blog pagination/topic/post routes are separate resource views and must retain canonical URLs. `/shop/[slug]` is dynamic; `/shop/` is an intentional production redirect to home, not a missing index to recreate.

Customer sign-in, cart, orders, checkout status/success and paid request/amendment forms stay separate from the staff shell and retain WhatsApp OTP. Checkout success wraps status semantics and should converge on one state component, preserving bookmarked return URLs. `/get` is secure delivery; `/drop-docs` is intake: opposite operations, not duplicate pages. Shipments is currently a product/availability page rather than a live tracking console; do not promise tracking without a real provider-backed contract. Preserve Privacy/Terms as public content and 404 as a real error experience.

Marketing pages such as Grahak OS, VayuLok and home should use the same brand tokens, header/footer and reusable feature blocks. Keep public navigation task-oriented: products, services, orders, help/account. Staff diagnostics should never be discoverable as customer actions. Price/availability claims require a product owner and deployment evidence; this audit does not activate unfinished offerings.

## Visual design research and specification

Use the existing dark green and lime brand in a quieter application shell. Neutral canvas, thin borders, compact tables and a lime highlight for the current location. Recommended 232–248px sidebar, 56px header, 24–32px main gutters, 44px comfortable interactive rows, one page header and one primary action. Avoid repeating full dashboard card grids for every resource. Inbox gets conversation list / thread / customer detail; operations gets filters / table / detail drawer; settings gets searchable groups / precise status / explicit configuration steps. Example data in the prototype is illustrative and never an AWS/customer snapshot.

This recommendation adapts [Carbon UI shell guidance](https://www.carbondesignsystem.com/building-blocks/core/components/ui-shell-left-panel/guidelines) for consistent global/secondary navigation and [Shopify's resource index pattern](https://shopify.dev/docs/api/app-home/latest/patterns/templates/resource-index) for lists, filters, resource states and contextual actions. These patterns can be implemented with existing React components; there is no need to import both component libraries.

Maintain stable ordering and consistent navigation labels per [WCAG consistent navigation](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation.html). Provide visible focus, skip link, labeled icons, keyboard search, accessible table headers, focus return from dialogs, and state messages. WCAG 2.2 [target-size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) is 24 CSS pixels or an applicable exception; 44px is our more comfortable design target. Do not use lime alone to indicate success/error. On mobile use a drawer, compact filters and a single primary pane; avoid mounting desktop side panels offscreen with active network polling.

Each integration record should distinguish **Not connected, Authorization required, Connected, Verification failed, Reconnect required**, and include provider identity, last successful authorized read, permission scope and next action. Infrastructure reachability is not OAuth authorization. “Persistent” means securely stored grants with renewal/reconnection handling, not a promise that providers can never expire/revoke access.

## Implementation order and release criteria

1. Fix contract/state defects W02–W10, prioritize cancellation, transcription availability and save confirmation. Capture existing capability tests before inbox consolidation.
2. Introduce a shared page/capability registry. Verify role-filtered sidebar/search, route existence and query active states. Keep existing URLs valid.
3. Build design tokens and three reusable page patterns: conversation, resource index/detail, settings. Pilot with Tasks and read-only invoice records; prove keyboard/mobile behavior.
4. Add paid service-request staff contracts and read-only queue; establish cursor paging and redaction. Add failed-message inspection after that; retain governance for replay.
5. Consolidate inbox, responses, identity, templates and Flow workflows incrementally. Use aliases/redirects and capability parity gates. Move developer references out of daily work.
6. Address content/SEO integrations and public shared components after operational workflows. Activate only supported backend capabilities.

For each migrated page: route/auth-role test; API verb/payload contract; distinct empty/error/forbidden/loading states; pagination and data freshness; keyboard/mobile layout; no unintended send/payment/configuration action on mount; telemetry to compare load time, request count and task completion. Measure bundle sizes and repeated polling before claiming savings. Fewer pages/menus does not automatically reduce AWS charges, and deleting a UI does not retire a Lambda safely.
