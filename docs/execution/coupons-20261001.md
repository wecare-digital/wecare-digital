# Coupons — native design reference

Coupons are created and held in our own DynamoDB table by our own Lambda, and are usable at
checkout. This file began as the 2026-10-01 coupons design note (revision 4, promoted here
2026-10-02). Revision 4 also described a coupon mirror on the retired storefront provider; that
integration was removed with the provider, so this version keeps only the native design. Sections
4 to 7 keep their numbers because `scripts/provision_coupons_*.py` and `tests/test_coupons_*.py`
cite them. The full revision 4 is in git history.

## Authority

The `CouponsTable` row is the sole authority for a coupon. There is no second copy anywhere to
reconcile against.

- `coupon_store.evaluate()` decides eligibility and answers with a **verdict** from a closed
  vocabulary, never a figure. A validate endpoint that returned a discount would be a number a
  browser could quote.
- `coupon_store.discount_paise()` is the single discount function. Native cart pricing
  (`catalog_pricing.coupon_discount_paise`) and the Pay Flow invoice path
  (`store_redemption_provider`) both call it: one definition, one reading.

Source of truth for everything below: `amplify/functions/shared/lambda_utils/ecommerce/coupon_store.py`,
`amplify/functions/ecommerce/coupons/handler.py` and the four `scripts/provision_coupons_*.py`
provisioners.

## 4. Data model

One table. Namespaced rows on a single partition attribute, the same shape `order_keys` uses,
because uniqueness has to be a conditional write on the partition key. A GSI is eventually
consistent and cannot enforce a constraint.

    stack-wecare-digital-CouponsTable      (env COUPONS_TABLE)
      partition key:  couponKey (S)        no sort key
      index:          status-index         status (HASH) + createdAt (RANGE), projection ALL, sparse
      billing:        PAY_PER_REQUEST
      PITR:           ENABLED, asserted by --verify
      TTL:            DISABLED, asserted by --verify

`status-index` is sparse: only definition rows carry `status`, so counters, holds and redemption
records never appear in it.

**TTL is disabled and that is load-bearing.** A coupon row records what discount was promised and
how often it was used. An expired coupon must stay readable long after it stops being applicable,
because a settled order references it. Expiry is a field, never a deletion.

**Drift gate.** There is no `Coupon` model in `amplify/data/resource.ts`, so
`scripts/check_data_model_drift.py` carries `CouponsTable` in `UNDECLARED_ALLOWED` with its reason
(the coupon service's issuance record, not part of the CRM data model). The name follows the
script's default rule, `Coupon → CouponsTable` (test 57).

### 4.1 Row types

```
COUPON#<codeUpper>                         the definition
COUPONUSE#<codeUpper>#<customerId>         per-customer usage counter
COUPONHOLD#<codeUpper>#<cartId>            a short-lived eligibility reservation (audit record)
COUPONREDEEM#<codeUpper>#<orderId>         idempotent terminal redemption record
```

`codeUpper` is the code NFKC-normalised and upper-cased; the exact `code` as issued is stored
separately for display. Normalising stops `SAVE10` and `save10` becoming two coupons that look like
one to a customer.

A coupon code is **not** bearer value. It is broadcast marketing material, so it may be logged in
full and is safe as a partition key. A gift-card code is the opposite, which is why the gift-card
store keys on an HMAC instead. `tests/test_coupon_logging_and_vocabulary.py` pins the asymmetry.

> **DECISION 5 — the hold existence fact lives on `COUPON#<codeUpper>`, not on the hold row.**
> The table has one partition attribute and no sort key, `dynamodb:Scan` is denied, and a `Query`
> needs partition-key equality, so "any row whose key begins `COUPONHOLD#<codeUpper>#`" cannot be
> asked. The fact therefore sits on the row whose key is always known: `activeHoldCartId` and
> `activeHoldExpiresAtMs`, and `hold()` is **one** conditional `UpdateItem`. `COUPONHOLD#` rows are
> written in the same request as audit records and are never read to make a decision. The
> gift-card store takes the identical decision for its card row.
>
> Consequence (HIGH-3): every DynamoDB access in `coupon_store.py` is an exact-key
> `GetItem`/`PutItem`/`UpdateItem`/`DeleteItem`, plus the staff `Query` on `status-index`, and
> nothing else. `tests/test_coupon_store.py` enumerates the module's access patterns and asserts
> zero `scan` call sites.

### 4.2 `COUPON#<codeUpper>` attributes

| Attribute | Type | Notes |
|---|---|---|
| `couponKey` | S | `COUPON#<codeUpper>` |
| `couponId` | S | UUIDv7 from `identifiers.new_uuid7`, internal |
| `code` | S | as issued, NFKC-normalised, case preserved, ≤ 20 chars of `[A-Za-z0-9._-]` |
| `name` | S | ≤ 100 chars |
| `status` | S | `ACTIVE` / `INACTIVE` / `EXHAUSTED` (the sparse index key) |
| `discountKind` | S | exactly one of `MONEY_OFF` / `PERCENT_OFF` / `FIXED_PRICE` / `FREE_SHIPPING` / `BUY_X_GET_Y` |
| `moneyOffPaise` | N int | `MONEY_OFF` only; a whole multiple of 100 |
| `percentOffBps` | N int | `PERCENT_OFF` only; a whole percent, so 500 == 5% |
| `fixedPricePaise` | N int | `FIXED_PRICE` only; a whole multiple of 100 |
| `buyX` / `buyY` | N int | `BUY_X_GET_Y` only |
| `minimumSubtotalPaise` | N int | optional; a whole multiple of 100 |
| `scopeNamespace` | S | `stores` |
| `scopeGroupName` | S | `product` / `collection`, absent for site-wide |
| `scopeEntityId` | S | required iff `scopeGroupName` is present |
| `startTimeMs` / `expirationTimeMs` | N int | epoch milliseconds; expiry must be after start |
| `usageLimit` / `limitPerCustomer` | N int | optional |
| `usageCount` | N int | atomic `ADD` |
| `activeHoldCartId` / `activeHoldExpiresAtMs` | S / N int | DECISION 5; a hold past its instant is void and may be taken over |
| `limitedToOneItem` | BOOL | |
| `tags` | L | optional, ≤ 100 strings |
| `currency` | S | `"INR"`, compared explicitly, never inferred from an amount |
| `policyVersion` | S | `coupon-policy-2026-10-01` |
| `createdAt` / `updatedAt` | N int | epoch seconds |
| `createdBy` | S | staff subject id |

Every money attribute is integer paise and every rate is integer basis points, bounded by
`money.py`'s ceiling `9007199254740991`. Every kind except `FREE_SHIPPING` needs a scope or a
minimum subtotal; `FREE_SHIPPING` may not carry a scope.

### 4.3 Counters and holds

- `hold(table, *, code, cart_id, ttl_seconds=900)` takes the hold with one conditional
  `UpdateItem` on the definition row (DECISION 5) and writes the `COUPONHOLD#` audit row.
- `release(table, *, code, cart_id)` needs the cart id to prove it owns the hold it clears.
- Usage counters are atomic `ADD`s on `COUPON#` (`usageCount`) and `COUPONUSE#` (`uses`).

### 4.4 Index

`status-index` serves the staff list (`GET /coupons?status=`) and nothing else.

## 5. Lambda surface

One function, `wecare-coupons`, with its own role (§6):

    amplify/functions/ecommerce/coupons/handler.py
    amplify/functions/shared/lambda_utils/ecommerce/coupon_store.py

### 5.1 Routes

| Route | Identity | Purpose |
|---|---|---|
| `POST /coupons` | staff | Create; uniqueness by `claim`'s conditional put |
| `GET /coupons/{code}` | staff | Our record |
| `GET /coupons` | staff | List by `status` via `status-index` |
| `POST /coupons/{code}/deactivate` | staff | `status=INACTIVE`; never deletes |
| `POST /coupons/validate` | customer session | Eligibility only; a verdict, never an amount. No route prices a coupon |
| `POST /coupons/hold` | customer session | `evaluate`, then `hold`; answers `held` and `expiresAtMs` |
| `POST /coupons/release` | customer session | Clears the hold |

There is no `DELETE /coupons/{code}`: deactivation is reversible and keeps the definition a settled
order references. The customer id always comes from the session, never from the body.
`POST /coupons/validate` is rate-limited per customer session through `lambda_utils/rate_limit.py`,
and `UNKNOWN_CODE` has the same answer shape as `EXPIRED`, so it cannot be used to enumerate codes.

The verdict vocabulary is closed: `ELIGIBLE`, `UNKNOWN_CODE`, `NOT_ACTIVE`, `NOT_STARTED`,
`EXPIRED`, `USAGE_LIMIT_REACHED`, `CUSTOMER_LIMIT_REACHED`, `HELD_BY_ANOTHER_CART`.

#### 5.1.1 The route provisioner — `scripts/provision_coupons_routes.py`

| | |
|---|---|
| API | HTTP API `zllr9lrg7j`, the account's only one |
| Stage | `prod` (auto-deploy; there is no `$default` stage) |
| Integration | `AWS_PROXY`, payload format `2.0`, target `wecare-coupons:live` — the alias, never `$LATEST` |
| Route keys | exactly the seven above; deliberately not a `{proxy+}` |
| Permission | one `lambda:InvokeFunction` statement per route, qualified to the alias, `SourceArn` scoped to the coupon paths |
| Idempotence | existing routes are reported, never recreated or retargeted; dry run is the default, `--apply` is required |

**Authorization posture.** All seven routes are `AuthorizationType=NONE` with no authorizer, like
every other route on this API. Authentication is inside the handler: Cognito `require_auth` with a
role on the staff routes, and the customer-session check on the customer routes, both before the
table is touched (test 62). Gateway configuration alone cannot distinguish an intentionally public
route from an accidentally public one, so the intent is stated here and pinned by test.

### 5.2 Commit

`coupon_store.commit_redemption(table, *, code, cart_id, order_id, customer_id)` records one
terminal redemption, idempotent on `(code, order_id)`. It runs after capture is verified, from the
function that performs the internal-order write; an `orderId` existing is itself the evidence that
money moved.

Order is load-bearing: the `COUPONREDEEM#` claim, then the counters, then the hold delete. The claim
is irreversible and the counters are not, so a crash between them leaves a correctly-claimed coupon
with an undercounted total, which a replay repairs. A counter the limit refuses is reported, not
raised: refusing after capture would leave a paid order with no redemption record. Eligibility is
refused earlier, by `evaluate` and `hold`. A repeat call returns `{"committed": False}` and touches
nothing.

#### 5.2.1 Checkout's role and its IAM self-check

Checkout does not import the coupon store, so `wecare-checkout-role` carries **no** `CouponsTable`
access (`scripts/provision_checkout.py`, `expected_role_policy`; test 52). The checkout
provisioner's IAM simulation covers every action its policy grants, so a grant cannot exist
without being measured (MEDIUM-18; test 52a), and `dynamodb:DeleteItem` stays denied on the
payment-attempt and commerce-keys tables (test 52b).

## 6. Scoped IAM

`scripts/provision_coupons_role.py` provisions `wecare-coupons-role` and the function's log group.
It is the function's own role, never the shared fleet role `wecare-digital-lambda-role`.

| Sid | Actions | Resource |
|---|---|---|
| `CouponIssuanceTable` | `dynamodb:GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `Query` | `CouponsTable` and its `status-index`; `DeleteItem` is for `COUPONHOLD#` rows only |
| `ValidateCustomerSession` | `dynamodb:GetItem`, `UpdateItem` | `stack-wecare-digital-CustomerSessionsTable` |
| `CouponRateLimit` | `dynamodb:UpdateItem` | `stack-wecare-digital-RateLimitTable` |
| `StaffRoleMembership` | `cognito-idp:AdminListGroupsForUser`, `AdminGetUser` | the staff user pool |
| `OwnLogGroup` | `logs:CreateLogStream`, `PutLogEvents` | `/aws/lambda/wecare-coupons` only |

No `dynamodb:Scan`, no `dynamodb:*`, no `DeleteTable`, no wildcard action or resource, and no
credential value in the document. The trust policy pins the source account, and the provisioner
reads back what it wrote.
